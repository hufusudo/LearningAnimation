# 交互演示设计方案：浏览器访问网页全流程

> **学科代号**：`net`　**badge**：多进程接力 · 四层泳道 · 协议累积
> **核心命题**：把散落在 408 各章的协议（ARP / DNS / TCP / HTTP）串成**一次回车引发的因果接力链**，让用户在 10 秒的动画后能一口气复述「输入 URL 到屏幕出像素」到底发生了什么、由谁完成、每步拿到什么。
> **认知目标（全片唯一）**：一次网页访问不是浏览器一个进程包干，而是 **5 种协议、3 个浏览器进程按固定时序接力**。
> **复习导向定位**：用户已系统学过 408，本片**不复述报文格式细节**，只回答「这个协议干什么用、怎么干、拿到什么」，把散点连成链。

---

## 一、演示核心逻辑与阶段划分

### 1.1 叙事主线

```
用户敲下回车
   ↓  序章  URL 分段：哪些字符交给 DNS，哪些交给 HTTP
   ↓  阶段1  ARP：目标 IP 有了，但网卡不认识它 → 问网关要 MAC
   ↓  阶段2  DNS：主机名不是地址 → 问 DNS 服务器要 IP
   ↓  阶段3  TCP：有了 IP 还要先建双向连接 → 三次握手
   ↓  阶段4  HTTP：连接就绪才谈得上要什么 → 请求 / 应答 → 解析渲染 → 子资源二次请求
五种协议全部点亮 → 结论落板
```

> **顺序说明（教学上易错点）**：本片把 ARP 放在 DNS **之前**，是为了讲清「包总要有个链路层目的地才能发出去」的物理前提；实际上二者**并行发生**（DNS 查询包同样要经过 ARP）。UI 提示中会显式点明这层并行关系，避免形成错误时序记忆。

### 1.2 阶段清单

| 编号 | 阶段名 | 叙事目的 | 预估时长 |
| :--- | :--- | :--- | :--- |
| 序章 | 【URL 分段解剖】 | 建立「一段 URL 里，不同字符归属不同协议」的分段意识 | ~1.8s |
| 阶段 1 | 【ARP 问路】每层都要有链路层地址 | 补上最易遗忘的网卡→网关一跳 | ~1.8s |
| 阶段 2 | 【DNS 问名】域名不是地址 | 产出 32 位 IP，形状为「去-回」 | ~2.0s |
| 阶段 3 | 【TCP 握手】先把管道建起来 | 三条斜线的独特形状，强化记忆锚点 | ~1.9s |
| 阶段 4 | 【HTTP 取页】建好管道才谈要什么 | 请求/应答 + 解析渲染 + 子资源并发 | ~2.8s |

**总计 ~10.3s**，控制在规范要求的 2～4 个核心阶段（序章不占名额）+ 1 个序幕之内。

### 1.3 阶段推进的累积逻辑

每阶段最后一拍（Beat 05）点亮右侧「协议清单」中对应条目，序号 ① ARP → ② DNS → ③ TCP → ④ HTTP。**先演后点**，让「清单」成为观众自己推导出来的答案而非提前给出的目录。最后一阶段结束时五行全亮，面板底部浮出总结句。

### 2.2 纵轴：四层泳道（自上而下 = 报文流动方向）

| 层 | class | 内容 | 常驻元素 |
| :--- | :--- | :--- | :--- |
| L1 服务器 | `.lane--server` | Web 服务器方块 | `.node--webserver` |
| L2 网络 | `.lane--net` | DNS 服务器、路由器、交换机 | `.node--dns`, `.node--router` |
| L3 客户端协议层 | `.lane--proto` | DNS / TCP / HTTP 三枚协议芯片 | `.chip--dns`, `.chip--tcp`, `.chip--http` |
| L4 浏览器进程层 | `.lane--proc` | UI 进程、网络进程、渲染进程 | `.proc--ui`, `.proc--net`, `.proc--render` |

> 顺序刻意的反直觉之处：**真实主机上「浏览器进程」在最下层靠内，「网络出口」在最上**。本片让斜线自下而上飞升（浏览器 → 网关 → DNS → 服务器），读者一眼看到「消息从哪台机器出发」。

**纵坐标（1920 基准，仅作比例参考，实现用百分比/flex）**：
L1 顶 `y=40`，L2 `y=150`，L3 `y=260`，L4 `y=400`，各层高 `h=88`，层间留白 `22px`。

### 2.3 横轴：时间

- 起点 `x=96`（泳道标题栏 `w-24` 之后），终点 `x = 视口宽 - 48`；
- 单条斜线最长时间跨度锁死为**可用宽度的 42%**，超出压缩而非溢出；
- 时间轴**不显示秒刻度**，仅在底部 `#progress-rail` 显示 5 段填充进度（序章 + 4 阶段）。

### 2.4 斜线（报文飞行）几何规则

- 斜线 = 从 `起点泳道右缘中点` 到 `终点泳道左缘中点` 的 45° 直线，附箭头；
- 距离越远斜线越平（视觉量化 RTT），实现为 `angle = atan2(Δy, Δx)`；
- **请求方向向上飞、应答方向向下飞**，颜色靠 `#E5E4DC` 细线 + 端点圆点区分，不靠颜色块堆叠；
- 同屏并行报文最多 3 条（HTTP 阶段子资源 3 条），紧贴呈平行小间距 `10px`，不额外开泳道。

## 三、各阶段《动作时序规格表》

### 序章：【URL 分段解剖】不同字符，归属不同协议

- **持续总时长预估**：~1.8s
- **核心叙事目标**：让用户看清 URL 里 `host` 段归 DNS、`path+query` 段归 HTTP，协议分工从第一秒就建立。

| Beat | 节拍阶段 | 目标对象选择器 | 属性变换目标 | 耗时 & 缓动 | 伴随次级运动 (Secondary) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **01** | 上下文建立 | `.url-input` | 由 `opacity: 0, y: 12px` 淡入上浮至原位 | 200ms (`power1.out`) | 四条泳道同步降至 `opacity: 0.35`，`.url-part` 逐段 `opacity: 0.3`（`stagger: 0.03s`） |
| **02** | 产生预期 | `.url-part[data-part="scheme"]` | 字符 `https` 提亮为 `text-indigo-700`，`scale: 1.06` | 150ms (`sine.out`) | 右侧浮出小字「决定用哪套协议栈」，从 `x: -6px` 淡入 |
| **03** | 核心动作 | `.url-part[data-part="host"]` → `[data-part="query"]` | `host` 段青绿高亮并抽出为 `.token[data-kind="host"]` 落入 `#timeline-root` 底部待发区；随后 `path`、`query`、`fragment` 依次点亮为 `text-amber-700` | 900ms (`power2.inOut`) | 每段点亮时向右射出一条 1px 引线至 `.part-owner` 标签，标注「→ DNS 阶段」/「→ HTTP 阶段」（`stagger: 0.08s`） |

| **05** | 状态确认 | `.url-input` | 整串收起为信封摘要 `GET /index.html HTTP/1.1` 置于 `#envelope-bar` | 220ms (`power1.inOut`) | 四条泳道恢复 `opacity: 1`；`#narrative` 标题切至「阶段 1 · ARP 问路」 |

### 阶段 1：【ARP 问路】网卡不认识 IP，先问网关要 MAC

- **持续总时长预估**：~1.8s
- **核心叙事目标**：让用户看到「目标 IP 已就位，但帧还需要链路层 MAC」，并记住广播问、单播答、结果进缓存。

| Beat | 节拍阶段 | 目标对象选择器 | 属性变换目标 | 耗时 & 缓动 | 伴随次级运动 (Secondary) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **01** | 上下文建立 | `.lane--proc` | 该泳道 `is-active`（`border-left-color` 亮为 `sky-600`），标题反白 | 200ms (`power1.out`) | 其余三泳道加 `.is-dim` → `opacity: 0.5`，`filter: grayscale(40%)` |
| **02** | 产生预期 | `.proc--net` | 微蓄力上浮 `y: -4px`、`scale: 1.05` | 180ms (`sine.out`) | ARP Request 信封 `.envelope[data-wire-id="arp-1"]` 从进程右侧滑出并悬停在 `#envelope-bar` 首格 |
| **03** | 核心动作 | `.wire[data-kind="broadcast"]` | 斜线自 `.proc--net` 上行至 `.node--router`，线宽 2px，末端箭头脉冲 1 次 | 700ms (`power2.inOut`) | 途经 `.lane--net` 时以 `radial-gradient` 泛红扩散一圈（`scale: 0.6→1.4`, 300ms）；信封内容淡入「目标 MAC: FF:FF:FF:FF:FF:FF」 |
| **04** | 落位沉淀 | `.wire[data-kind="unicast"]` | 应答斜线自 `.node--router` 下行至 `.proc--net`；MAC 抽为 `.token[data-kind="mac"]` 落入 `.arp-cache` 表格首行 | 500ms (`power2.inOut`) | `.arp-cache` 行从空态 `height: 0 → auto` 展开（240ms `power1.out`），网关 IP ↔ MAC 配对文字 `stagger: 0.05s` 逐字出现 |
| **05** | 状态确认 | `.proto-item[data-proto="arp"]` | 加 `.is-lit`，序号 ① 亮为 `text-amber-700`，附注「→ 网关 MAC」淡入 | 250ms (`power1.inOut`) | 所有泳道取消 `.is-dim`；`#narrative` 切至「阶段 2 · DNS 解析」，Callout 换为「ARP 表有缓存时可直接命中，不再广播」 |

### 阶段 2：【DNS 问名】域名对路由器无意义，必须换成 IP

- **持续总时长预估**：~2.0s
- **核心叙事目标**：展现「去-回」两段斜线的请求应答形状，并强调产出物只有一个 32 位地址。

| Beat | 节拍阶段 | 目标对象选择器 | 属性变换目标 | 耗时 & 缓动 | 伴随次级运动 (Secondary) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **01** | 上下文建立 | `.proc--net` | `is-active`；`.token[data-kind="host"]` 从待发队列提亮 `scale: 1.05` | 200ms (`power1.out`) | 其余泳道 `.is-dim`；右下角浮出「解析器调用栈」小卡：`浏览器 → OS 解析器 → 缓存查询` |
| **02** | 产生预期 | `.chip--dns` | `.proc--net` 内 DNS 芯片亮起并脉冲 | 300ms (`power1.out`) | 三级缓存卡（浏览器 DNS 缓存 → hosts → 本地 DNS）自上而下 `stagger: 0.06s` 逐格点亮后全部熄灭，标注「未命中」 |
| **03** | 核心动作 | `.wire[data-kind="req"]`，`.wire[data-kind="rsp"]` | 请求斜线上行至 `.node--dns`，应答斜线下行返回，两条线间隔 `<= 0.15` | 900ms (`power2.inOut`) | 请求斜线行时信封显示「DNS 查询 · id 0x3F2A · UDP:53 → src」；应答行时追加「A 记录 · ttl 300 · 4 字节」 |
| **04** | 落位沉淀 | `.token[data-kind="ip"]` | 应答中的 A 记录值抽出为 IP 令牌，落在 `.node--dns` 与 `.proc--net` 之间的地址带上，脉冲一次 | 300ms (`back.out(1.2)`) | 令牌同时写入 `.dns-cache` 表格；同时 `.chip--tcp` 首次呼吸式预亮（提示下一步） |
| **05** | 状态确认 | `.proto-item[data-proto="dns"]` | `.is-lit`，序号 ② 亮，附注「→ 目标 IP」 | 250ms (`power1.inOut`) | 泳道解除降权；`#narrative` 切至「阶段 3 · TCP 三次握手」；Callout：「UDP 无连接，也不可靠，但单次查询足够短小」 |

### 阶段 3：【TCP 握手】先把双向管道建起来，才谈得上要什么

- **持续总时长预估**：~1.9s
- **核心叙事目标**：用**三条斜线**这一独特形状作为记忆锚点，并与阶段 1、2 的两段斜线形成形状对比；强调「连接」是独立于 IP 的资源。

| Beat | 节拍阶段 | 目标对象选择器 | 属性变换目标 | 耗时 & 缓动 | 伴随次级运动 (Secondary) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **01** | 上下文建立 | `.proc--net` | `is-active`；IP 令牌右移贴上 socket 槽位 | 200ms (`power1.out`) | 其余泳道 `.is-dim`；`#narrative` 浮出「IP 只是门牌，TCP 才是双向管道」 |
| **02** | 产生预期 | `.token[data-kind="syn"]` | `.proc--net` 内 SYN 段蓄力上浮，`y: -4px`、`scale: 1.05` | 180ms (`sine.out`) | 对端 `.node--webserver` 同步蓄力，双向呼应 |
| **03** | 核心动作 | `.wire[data-kind="handshake"]`（3 条） | ① 客户端→服务器 SYN(seq=x)；② 服务器→客户端 SYN+ACK(seq=y, ack=x+1)；③ 客户端→服务器 ACK(x+1)。每条相对偏移 `<= 0.12` | 1000ms (`power2.inOut`) | 三条信封在 `#envelope-bar` 内按序点亮并各自显示 `seq/ack` 数值；服务器泳道在收到②时短暂提亮 |
| **04** | 落位沉淀 | `.tcp-socket` 指示灯 | 客户端与服务端连接灯由 `pulse-led-amber` 切换为 `pulse-led-emerald` | 300ms (`power1.out`) | 双向箭头首尾各生成一个小括号形「连接」标记，`scale: 0.8→1`（`back.out(1.4)`） |
| **05** | 状态确认 | `.proto-item[data-proto="tcp"]` | `.is-lit`，序号 ③ 亮，附注「→ 双向连接」 | 250ms (`power1.inOut`) | 泳道解除降权；`#narrative` 切至「阶段 4 · HTTP 请求与渲染」；Callout：「建链成本真实存在，所以 HTTP/1.1 要复用连接」 |

### 阶段 4：【HTTP 取页】管道就绪，才开始谈要什么

- **持续总时长预估**：~2.8s
- **核心叙事目标**：完成「请求 → 应答 → 解析 → 像素」最后一跳，并让用户看到**解析过程中发起的子资源并发请求**（3 条平行斜线）。

| Beat | 节拍阶段 | 目标对象选择器 | 属性变换目标 | 耗时 & 缓动 | 伴随次级运动 (Secondary) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **01** | 上下文建立 | `.proc--render` | 渲染进程泳道 `is-active`；渲染进程内空白文档区 `opacity: 0.3` 待填充 | 200ms (`power1.out`) | 其余泳道 `.is-dim`；`#narrative` 浮出「此刻 UI 与网络进程待命，渲染进程准备接管」 |
| **02** | 产生预期 | `.wire[data-kind="req"]`（HTTP） | 请求行微浮，`y: -4px`，信封预览 `GET /index.html HTTP/1.1` | 200ms (`sine.out`) | 序章存下的信封摘要在 `#envelope-bar` 高亮对齐 |

## 四、边缘情况预防清单

| 类别 | 场景 | 预防措施 |
| :--- | :--- | :--- |
| **数据溢出** | 域名超长（12 级子域名） | `.envelope` 文本 `truncate` + `title` 提示；**泳道高度恒定**，绝不随文本增长 |
| **数据溢出** | 页面含 50+ 子资源 | 子资源斜线固定 3 条代表（`css/js/png`），多余项在信封条带折为「+N」徽标，不铺满舞台 |
| **连线断裂** | 斜线端点落在节点边框外侧 | 端点统一按节点 bounding box 计算（含 6px 边距），斜线终点永远指向节点边缘而非中心 |
| **连线断裂** | 节点尺寸随状态变化导致斜线错位 | 节点尺寸变化时，用 `gsap.quickTo` 同步重算斜线端点，或将节点尺寸变化纳入同一 timeline 的同一拍 |
| **元素碰撞** | 3 条平行斜线与信封条带重叠 | 斜线绘制区与 `#envelope-bar` 严格分层（`z-index` 分离），斜线区下边界距条带上边界 ≥ 12px |
| **元素碰撞** | 泳道标题与斜线起点重叠 | 标题栏固定 `w-24`，斜线起点 x 恒 ≥ `w-24 + 8px` |
| **竞态清理** | 连点「下一步」或「播放/暂停」 | 每次状态切换前 `gsap.killTweensOf('#timeline-root *')` + `gsap.globalTimeline.clear()`，防止补间叠加（AGENT.md §3.5） |
| **竞态清理** | 切阶段后残留高亮 | `setPhaseActive(idx)` 统一重置所有 `.lane` 的 `is-active` / `is-dim`，只留目标态 |
| **重播一致性** | 播完回到阶段 0 状态不干净 | 每个 Phase 的 timeline 以 `fromTo` / `set` 显式写回初态，禁止依赖上一阶段结束状态 |
| **视口自适应** | 窗口缩放 / 笔记本小屏 | SVG 用 `viewBox + preserveAspectRatio="xMidYMid meet"`；`resize` 时重算斜线角度与可用宽度百分比（AGENT.md §3.6） |
| **速度倍率** | 切到 2x 时子资源并行段被跳过 | 所有 duration 取自 `State.speed` 统一缩放，禁止在单拍内写死毫秒（AGENT.md §3.4） |
| **可访问性/降级** | CDN 失败 GSAP 未加载 | 面板显式提示「动画引擎未加载，页面已降级为静态图解」，不白屏 |
| **教学准确性** | 用户误以为 ARP 必在 DNS 之后 | 序章 Callout 显式提示「二者实际并行」；`#narrative` 中标注「为叙事分开展示」 |

## 五、技术架构与交接契约

### 5.1 目录与文件

```text
浏览器访问网页全流程/
├── index.html   # HUD + 三栏骨架 + SVG 泳道
├── style.css    # 泳道、信封、协议清单、Callout
└── app.js       # 几何计算、阶段时间轴、控制器
```

技术栈：Tailwind CDN + GSAP 3.12.5 CDN + 原生 ES6，**零构建**，`file://` 可直接打开。

### 5.2 强制约束

1. **禁 `setTimeout` / `setInterval` 控制动画**；一切走 GSAP timeline；
2. 每阶段一个子时间轴 `getPhaseTimeline(phaseIndex)`（0=序章，1~4=四阶段），主控制器 `MasterController` 统一调度；
3. Beat 间一律用相对偏移量衔接（`<+=0.05`），禁止裸延时；
4. 支持打断 / 重播 / 前进 / 后退（上一阶段、下一阶段、复位）；
5. **全自动连播**：一键从当前阶段连续播到最后一阶段，阶段衔接由子时间轴 `onComplete` 回调驱动，**不引入任何定时器**；连播中按上一步 / 下一步 / 复位 / 播放 即退出连播并交还手动控制；末阶段播完自动退出连播并呈满灯终态；
5. 斜线几何集中在 `computeWire(fromRect, toRect, maxSpanRatio)` 单一函数，杜绝散落魔法数字；
6. duration 全部读取 `State.speed` 动态缩放；
7. Beat 采用**绝对毫秒锚点**排布（`at(ms)`），禁止依赖 `>` / `<` 相对定位——相对定位会向时间轴起点塌缩，导致实测时长腰斩、Beat 次序错乱。

### 5.3 两步实现法（交由编码阶段 AI 执行）

- **Step 1（先不做动画）**：只搭 `index.html` + `style.css` 静态骨架，四条泳道、五条清单项、空信封条带全部就位；验证 1280 / 1920 / 2560 宽度下无重叠、无横向滚动；输出后停下等确认。
- **Step 2（确认布局后）**：按第三章规格表逐 Beat 落地 `gsap.timeline()`，补 `computeWire` 与状态机。
